# 開発方針

ガイドサイトを、製品方針、開発予定、利用方法の共有先とします。[コンセプト](./concept)と[ビジネスモデル](./business-model)を踏まえ、このページでは実装時の設計原則と受け入れ条件を扱います。顧客向けガイドとともにメンテナンスし、要件が重複する別立てのPRDは作りません。

## 設計原則

- **手間を小さくする：** 導入、学習、日常運用、久しぶりに戻るときの負担を減らします。静かな見守りのために、毎日ダッシュボードを開く必要はない設計とします。
- **判断に役立てる：** 通知数より確認する価値を重視します。理由、根拠、推定効果、次の行動を示します。
- **安全に進める：** 適した準備・整理を自動化します。危険な変更は無断で実行せず、推定効果と実現済みの削減を区別します。
- **総コストを抑える：** 採用済みのCloudflare優先の構成を活用し、範囲を絞ります。インフラ費だけでなく保守、顧客対応、セキュリティ、信用獲得も費用として評価します。
- **信頼と選択を守る：** 根拠を確認でき、データ共有には同意がある設計とします。小さな黒猫は業務を邪魔しない範囲で使い、前向きで正確な表現を守ります。

[採用済みの技術と責務分離](./index#主なアーキテクチャ)を維持します。TanStack Start、oRPC、`packages/auth`のBetter Auth、`packages/core`の業務ロジック、`packages/db`のDrizzleとD1を使い、pnpm WorkspaceとVite+で管理します。他のプロバイダーやブラウザ側のDuckDB WASMは、Cloudflareが要件に合わない場合の選択肢であり、追加の採用決定ではありません。

## 開発範囲と受け入れ条件

現在のリポジトリには、ガイドサイトとアプリ・パッケージの土台があります。顧客向けFinOpsの業務フローは未実装です。Google Cloud連携セットアップと初回診断を**v0.1予定・未提供**として定めます。Hello World、挨拶のAPI、認証・DBの初期化関数を、製品リリースとして扱いません。

機能の開発が決まったら、顧客向けガイドに目的、予定される操作、期待結果、制約、対象バージョン、提供状況を追加します。同じ変更で、ここに必要な設計と受け入れ条件を記録します。実装時にはガイドの期待結果をシナリオテストへ結び付けます。実際の動作を検証し、制約を記載してから、試験提供・提供中へ更新します。

確定した流れは、設定 → 接続と権限の確認 → 対象を限定した取得 → 評価 → 改善候補と根拠の確認です。方式案、ルール選定、データ管理、提供前の条件は[Google Cloud連携の設計](./google-cloud)と[初回診断の設計](./diagnostics)に記載します。少数のルールで取得を共有し、1種類だけへの制限も全ルールの提供も要件にはしません。

v0.1には、自動リソース変更、AWS・Azure、リセラー紹介の実装、植林、感謝、バッジ、プロフィール、高度な配賦・社内請求、全モック画面・全ルール、定期実行、Slack通知を含めません。仮想分類と簡易Showbackは優先度を下げた候補として残し、対象バージョンは未定です。

以下の一般原則は、それぞれの範囲を採用した際に適用するもので、v0.1を拡張するものではありません。

| 決定した範囲に含まれる場合 | 確認すること                                                                     |
| -------------------------- | -------------------------------------------------------------------------------- |
| 導入やクラウド接続         | 必要な権限・設定と、成功・失敗が分かる。導入方式は先に選定する。                 |
| 改善候補の提示             | 理由、根拠、推定の前提、次の行動を確認できる。推定と実現済みの結果が区別される。 |
| 見守りや通知               | なぜ確認すべきかと次の行動が分かる。頻度と関連性の基準を提供前に定める。         |
| クラウドリソースの変更     | 必要な認可を強制し、危険な変更が無断で実行されない。                             |
| 見積もり依頼や紹介         | 関係性、共有先、共有データが明確。同意しなければ何も送信されない。               |

`v0.1予定・未提供` / `v0.1 planned · Not available`のように、バージョンと提供状況を併記します。予定の表記は確定したGoogle Cloudの体験に適用しますが、利用開始の告知ではありません。開発範囲と実装が変わるたびに両言語を揃えます。

## 仮想分類と簡易Showbackの設計条件

リソースを変更しない費用分類・共有を製品の方向とし、仮想タグ・仮想ラベルと簡易Showbackを機能候補として具体化します。未提供で、対応クラウド、無料範囲、対象バージョン、配賦方法は未定です。採用時には以下を受け入れ条件へ落とし込みます。

- 取得した費用データにLuckyCat内の分類を重ね、リソースの設定・タグやTerraformへ書き戻さない。仮想分類は移行期の整理にも、費用管理固有の継続的な分類にも使える設計とする。
- 分類ルールを試し、対象金額・未分類額・分類根拠を確認できる。取得データにない粒度を推測で確定扱いせず、共有費用には配賦ルールと根拠を示す。
- 簡易Showbackはチーム別費用と根拠の共有を扱う。閲覧範囲をサーバー側で制御し、許可されていないチームの費用を表示しない。複雑な社内請求・会計処理は対象に含めない。
- 実装時に、分類前後の金額の整合性、未分類の扱い、リソースへの書き戻しがないこと、閲覧範囲を越えたアクセスの拒否を検証する。

## 未決定事項と検証課題

- **v0.1の詳細：** 個別ルールの採用、閾値、対応するリソースの詳細な種別、時期。Google Cloudと初回診断の流れは確定です。
- **提供方法：** 認証方式、正確な権限・API、保存・削除、取得上限、金額の根拠。連携・診断ページの提供前条件を満たしてから提供します。
- **配布：** 製品ライセンスと本番セルフホストの支援。

該当する開発が承認された時点で具体化します。価格、採算、提携などの検証課題は[ビジネスモデル](./business-model#成立条件と検証課題)で管理します。
