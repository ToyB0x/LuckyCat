# Google Cloud連携の設計

::: info v0.1予定・未提供
初回の対応クラウドはGoogle Cloudです。連携設定、アクセス確認、対象を限定したデータ取得、初回診断が確定した体験です。認証方式、正確なIAM設定、個別ルールの採用は提案段階で、この業務フローは未実装です。

## 接続方式の検証案

LuckyCatのワークロードを表すOIDCのIDと短期のGoogle Cloud認証情報を使う、Workload Identity Federation（WIF）を優先して検討します。顧客が所有する連携設定と専用の読み取りサービスアカウントを用い、権限借用する構成を初期案とします。Googleは直接のリソースアクセスとサービスアカウント経由の両方に対応しているため、採用APIと顧客の設定負担を確認して選びます。これはLuckyCatの設計案であり、権限借用が常に必須という意味ではありません。[WIFの概要](https://docs.cloud.google.com/iam/docs/workload-identity-federation)を参照してください。

信頼できる発行者、署名鍵の保護とローテーション、変更されない組織・ワークロードの識別子が必要です。発行者、audience、subject、顧客組織、接続、許可プロジェクトをサーバー側で結び付けます。リクエストに含まれるプロジェクトやサービスアカウントの指定で、別の顧客の認証情報を選べてはいけません。同じ発行者を使う全テナントを一括して信頼しません。Googleの[SaaS連携の要件](https://docs.cloud.google.com/iam/docs/use-workload-identity-federation-to-let-customers-access-their-cloud-resources)と[OIDCプロバイダーの設定](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-providers)に照らして設計します。

Cloudflareでホストするだけで、この設計のOIDC発行者が用意されるとは扱いません。発行者の実装またはサービス、トークン更新、実行環境との互換性、運用負担を検証してから採用します。顧客のGoogle Cloud鍵を保存しない構成でも、LuckyCat自身の署名用認証情報の保護は必要です。

| 別の方式 | 位置付け |
| --- | --- |
| ユーザーの権限を委任するOAuth | WIFの設定負担が大きい場合に比較する。同意、スコープ、トークンの保存・取り消し、ユーザーの退職、必要な審査などの設計が別途必要。未採用。 |
| ローカルCLI・Application Default Credentials | ローカル開発の手段であり、顧客向けWeb接続の仕様にはしない。 |
| 長期サービスアカウント鍵のアップロード | 標準の導入方法にはしない。連携方式の未決定を回避するための近道として追加しない。Googleも[可能な場合はユーザー管理の鍵を避ける](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)方針を示している。 |

## セットアップと実行時の権限

顧客側の管理者が、信頼設定、サービスアカウントのアクセス、必要なAPIを準備します。実行時のIDは、採用したルールに必要なデータだけを読み取ります。プロジェクト管理、IAM変更、API有効化、リソース変更の権限を与えません。

WIF案では、IAM、Security Token Service、Service Account Credentialsと、設定時に関わるResource ManagerのAPIを採用フローに照らして確認します。初回のリソース候補にはCompute Engine APIが必要です。最終的なAPI一覧、有効化するプロジェクト、信頼設定、最小限のロールは、セットアップを検証してから公開します。請求エクスポートとBigQueryの権限は、ルール単位の追加要件とします。

認証の成功と、必要な取得元ごとの限定的な読み取り確認を分けます。対象と確認時刻を記録し、権限拒否、API無効、クォータ制限、認証の期限切れ、一時的な失敗を区別します。確認の失敗に応じてIAMやAPIを自動変更しません。確認操作だけで、全件取得や将来のアクセスを保証しません。

## 既存構成での責務

- `packages/auth`はBetter Authを通じて、LuckyCatのセッションと組織・対象範囲の認可を扱う。LuckyCatへのログインとGoogle Cloudを読み取る権限は別。
- `apps/api`は、認可した接続・診断の操作とサーバー側のGoogle Cloudアダプターを組み合わせる。クラウドトークンはサーバー側に限定し、接続設定で任意の外部URLへ送信できないようにする。
- `packages/core`は、データ取得のインターフェースを通じて評価と結果の意味を扱い、Cloudflare、Google SDK、HTTPに依存しない。
- `packages/db`は永続化を扱う。データスキーマ、保存期間、削除は未実装。

ワークロードのIDトークンの発行・署名と、連携時のトークン交換を集約する、サーバー専用の`packages/oidc`を追加候補とします。採用する場合、`apps/api`はそのインターフェースを利用し、リソース取得は引き続きAPI側、Better Authのセッションと認可は`packages/auth`で扱います。パッケージの採用、正確な責務の境界、接続方式は未確定であり、今回のガイド更新ではパッケージを作成・必須化しません。

## 安全性とデータ管理

実顧客データを受け入れる前に、以下を満たします。

- 権限、取得フィールド、保存する根拠を採用ルールに必要な最小限にする。リソース一覧の確認に、ディスクの中身、オブジェクト本文、環境変数、アプリケーションの秘密情報は不要。無関係なメタデータ項目も取得しない。
- 接続作成、確認、診断、結果閲覧を、組織と明示したプロジェクト・リソース範囲で認可する。認証情報、キャッシュ、保存結果、取得リクエストにも同じ境界を適用する。
- 同意前に取得内容と送信先を説明する。接続しただけでは、広範な探索、診断、未説明の外部送信を始めない。明示的な接続確認で許可されるのは、説明済みの確認操作だけとする。
- 認証情報や不要な生レスポンスをログ、画面、エラー、サポート用出力へ出さない。許可された必要な根拠だけを表示し、プロバイダーのエラーをそのまま露出させない。
- 取得前に、保存期間、保存場所、削除方法、解除後の結果・バックアップの扱いを決める。推測した保存期間や無期限保存を初期値にしない。
- プロジェクト数、ページ数、リソース数、処理時間、同時実行数、再試行、費用・クォータ消費を制限する。取得打ち切りと部分取得を表示し、上限付きの待機・再試行を行う。恒久的な権限エラーを繰り返し再試行しない。
- 解除で新しい取得とトークン更新を止め、実行中の処理の停止方法を定める。発行済みトークンの有効期間や反映時間を含むクラウド側の取り消しは別に説明する。LuckyCat内のキャッシュを無効化し、保持した認証情報の再利用を防ぐ。保存結果の削除は別のライフサイクルとして扱う。

読み取り診断が除外するのはリソース変更であり、APIリクエスト、クエリ実行、顧客側の費用ではありません。[Computeの読み取りクォータ](https://docs.cloud.google.com/compute/api-quota)や、追加利用する場合の[BigQuery保存・クエリ料金](https://cloud.google.com/bigquery/pricing)を考慮し、クエリを許可する前に予算と上限を承認します。

| 判断・検証事項 | 提供前に満たすこと |
| --- | --- |
| 認証と導入 | WIFまたは別方式を選び、発行者の運用、顧客の準備負担、正確な権限・API、組織ポリシーとの適合性を確認する。 |
